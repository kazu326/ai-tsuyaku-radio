# AI通訳ラジオ｜Model / Resource Policy v0.1

## 1. 目的

AI通訳ラジオでは、常に最も高性能なモデルを使うことを目的にしません。

目標は、**品質を落とさない範囲で、必要十分な知能と計算資源を使うこと**です。

評価するのは、単純なトークン単価ではなく、**完成したタスクあたりの品質・修正回数・時間・コスト**です。

## 2. 最重要原則

### 最小十分な知能を使う

簡単な作業へ高コストなモデルを使い続けません。

一方、安価なモデルへ無理に任せて、修正回数が増える、人間の確認負担が増える、誤りを見逃す、結果的にやり直すのであれば、安くなったとは考えません。

**最終的にタスクを完了するまでの総コスト**で判断します。

## 3. モデル名を固定ルールにしすぎない

モデルの性能・価格・利用環境は変化します。

そのため、「この作業は永遠にLuna」「この作業は必ずSol」のような固定表ではなく、**作業の難易度・不確実性・影響範囲**を基準に選びます。

現在の環境でモデル選択や委譲が可能な場合は、Luna級 / Sol級などの能力差を利用します。

## 4. 軽量モデルを優先する作業

既知のルールに従えば処理でき、判断の幅が小さい作業は軽量モデルを優先します。

例：
- ファイル名変更
- 決まった形式への変換
- JSON / Markdownの整形
- 既知テンプレートへの値の入力
- 字幕データの形式変換
- 採用済みルールに沿った単純な字幕改行
- 重複チェック
- ファイル一覧整理
- 既知のコードパターンの小さな変更
- 大量の反復処理
- 既に人間が決めた内容の実装

重要なのは、**考えなくてよい作業を高い知能へ投げない**ことです。

## 5. 上位モデルを優先する作業

曖昧さが大きい、失敗時の影響が大きい、複数の情報を統合する必要がある作業は上位モデルを優先します。

例：
- 新しいテーマの核心を決める
- 台本構成を考える
- 難しい技術を正確に簡略化する
- Meaning Cluster / Visual Segmentの境界を判断する
- 新しいVisual Planを設計する
- 未知の不具合を調査する
- 複数ファイルの設計矛盾を判断する
- 共通文法を更新するか判断する
- 新しい制作フローを設計する
- 重要な最終レビュー
- 何を次に検証すべきか決める

## 6. エスカレーション

軽量モデルで作業を開始しても、次の状態になった場合は上位モデルへの切り替えを検討します。

- 判断に確信が持てない
- 文書同士が矛盾している
- ルールの解釈が複数ある
- 重要な品質判断が必要になった
- 2回以上同じ修正を繰り返している
- 人間レビューで大きなズレが出た
- 既存ルールでは処理できない新しいケースが出た
- 変更の影響が複数ファイル・複数工程へ広がる

上位モデルを使うこと自体を失敗とは考えません。必要なところだけ上げることを正常な運用とします。

## 7. デエスカレーション

上位モデルが、方針を決めた、判断基準を作った、実装方法を確定した、不確実性を解消した後は、残った単純作業を軽量モデルへ戻して構いません。

例：

上位モデル → Visual Planを決定

軽量モデル → 決定済みPlanから字幕JSONを整形 → ファイル名を更新 → 定型コードへ値を入れる

という分担を許容します。

## 8. オーケストレーション

複数モデルを自律的に使い分けられる環境では、**上位モデルがすべてを自分で処理する必要はありません。**

上位モデルは、仕事を分解する、難易度を判断する、軽量モデルへ委譲する、必要な結果だけ確認する、不確実な箇所だけ自分で再判断する、という役割を取って構いません。

ただし、環境としてモデル切り替えや委譲ができない場合に、できると仮定して進めません。

## 9. 人間への確認

モデル選択を毎回人間へ聞く必要はありません。

品質・権限・予算の範囲内でAIが判断して構いません。

ただし、大量の高コスト処理、長時間の反復処理、予想以上の再試行、新しい外部APIの大量利用、大きな料金が発生する可能性がある場合は、人間への確認を検討します。

## 10. 記録する項目

将来的にモデルルーティングを改善するため、必要に応じて次を記録します。

- Task
- 使用モデル / 能力クラス
- 入力規模
- 実行時間
- トークン / コスト
- 修正回数
- 人間の修正量
- PASS / FAIL
- 上位モデルへの切替有無
- 最終的に十分だったか

すべてを毎回細かく記録する必要はありません。モデル選択の改善に役立つタスクから蓄積します。

## 11. 評価指標

単純な「安かった / 高かった」では判断しません。

理想的には、**Quality × Speed × Cost per Complete Task**で見ます。

例えば、軽量モデルは安いが3回修正、上位モデルは高いが一発でPASS、という場合、最終的な総コストと人間負担まで含めて比較します。

## 12. 現段階の運用

現時点では、詳細な自動ルーティング表を固定しません。

まず制作を続けながら、
- どの仕事は軽量モデルで十分か
- どこから上位モデルが必要か
- どの仕事で修正回数が増えるか

を観察します。

観察結果が蓄積した後、必要ならルーティング基準を更新します。

## 13. 判断原則

モデル選択で迷った場合は、**必要な品質を満たす最も軽い選択肢から始め、必要なら上げる**を基本とします。

ただし、失敗リスクや人間の再作業が大きい重要判断では、最初から上位モデルを使って構いません。

最適化する対象はトークン数そのものではありません。

**人間1人＋AIで、品質を維持しながら継続的に動画を作れること**を最優先します。
