# EPISODE SCRIPT WORKFLOW｜エピソード台本制作フロー v0.1

最終更新：2026-10-02

## この文書の役割

新しいチャットで「Episode 007を作成してください」のような短い依頼だけを受けた場合でも、既存の流れを読み取り、AI通訳ラジオらしい台本制作を開始できるようにするための入口。

これは台本を同じ型へ固定するテンプレートではない。毎回のテーマに合わせて判断しながら、調査、編集、レビュー、保存の順序と境界だけを共有する。

台本完成後の音声・映像制作で共通して参照する制作ルールも、この文書の「台本完成後：音声・映像制作の共通ルール」に置く。

## 開始時に読むもの

1. `context/CURRENT.md`
2. `context/EDITORIAL.md`
3. 直前エピソードの `script.md` と `research.md`
4. `CURRENT.md` または直前の次回予告から直接指定された資料

最初から全エピソード、全ログ、全コンテキストを読まない。テーマ、流れ、正本を判断するために必要なファイルだけ追加で読む。

## 短い依頼からテーマを決める

- 直前回の次回予告、Knowledge Masterの接続計画、`CURRENT.md` の合意済み方向を照合する。
- 合理的に一つへ絞れる場合は、追加質問をせず制作を進める。
- 複数の候補で核心が大きく変わり、既存情報でも決められない場合だけ確認する。
- 指定された回より先のエピソードは作らない。必要なら次回予告と接続候補だけを残す。

## 調査

1. 今回の中心となる「なぜ／どういうことか」を一問にする。
2. 最新性がある事実は、企業公式、政府機関、公式文書、論文などの一次情報で確認する。
3. 事実、当事者の説明、外部の推定、噂、制作側の解釈を分ける。
4. 制作側では深く調べるが、調べた情報を台本へ全部入れない。
5. 後から検証できるよう、採用しなかった重要情報と表現上の注意も `research.md` に残す。

## 一つの核心

台本を書く前に、視聴者が一つだけ持ち帰る文を決める。

- 一度聞いて理解できる文にする。
- 企業名、数字、専門用語を並べた要約にはしない。
- 各章は核心へ近づく役割を持たせる。
- 面白くても核心を増やす寄り道は、次回候補、記事、画面注釈、Knowledge Masterへ分ける。

## 発見型の語り

正しい説明を疑問文で包むだけでは、発見型の語りにはならない。語り手自身が、一度考えた答えを更新する必要がある。

確認するのは疑問文の数ではなく、次の変化である。

`初心者にも自然な仮の答え → それでは説明できない事実や矛盾 → 更新された理解`

語り手は先生として完成した答えを順番に配るだけでなく、視聴者より一歩先で確かめる同行者になれる。ただし、次の表現を固定ルールにしない。

- 「僕は最初」「僕はここで」の反復
- 各章を疑問形の見出しにすること
- 毎回同じ回数だけ認識を覆すこと
- 好奇心を見せるための作為的な驚きや猫ジョーク

テーマによっては、時間の流れ、具体的な事件、一つの実験、物の動きが発見を運んでもよい。重要なのは、視聴者の理解が途中で本当に変わること。

## 音声台本の自己レビュー

- 数字、年号、企業名、国名、専門用語が耳だけで追える量か。
- 名前を残す場合、世界構造や因果関係を理解する役割があるか。
- 一つの比喩を近い章で重ねていないか。
- 同じ意味を別の言葉で複数章に置いていないか。
- 一つの核心から外れる説明がないか。
- 初心者が前の文を読み返さず、現在地を追えるか。
- 説明の順番ではなく、興味、矛盾、発見のどれかが次の章を開いているか。
- 技術的に正しくても、資料の読み上げになっていないか。
- 音声で聞いた瞬間に一度理解が止まる専門語や業界表現がないか。たとえば「モデルの重み」を消すのではなく、「学習した結果」→「モデルの重み」の順に理解させる。「重みを開く」のような業界的・直訳的な表現は避け、必要なら「公開する」など普通の日本語へ戻す。

## 人間の赤ペンを受けた後

1. `KEEP` は、文言だけでなく機能も壊さない。
2. `FIX` は指摘された範囲へ絞り、構成全体を勝手に変えない。
3. `WATCH` は固定ルールへ昇格させず、次回の観察点として残す。
4. 技術的な誤解を防ぐ修正は、伝えたい因果関係を残した最小変更にする。
5. 別エピソードでも同じ判断が自然に確認され、人間側にも認識された場合だけ、World Modelや猫の足跡への昇格を検討する。

## 台本完成後：音声・映像制作の共通ルール

Episode 006までの制作で確認された共通制作ルール。2026-09-27に `context/CURRENT.md` へ記録されたが、2026-10-01の更新で削除されたため、ここへ移して正本とする。全体の制作フローは `context/CURRENT.md` の「Season 1終了時点の制作フロー」を参照する。

### 音声の「はい＋ロングポーズ」

ElevenLabsで各音声を生成するとき、本番セリフの前に「はい」＋約1秒のロングポーズ、本番セリフの後に約1秒のロングポーズ＋「はい」を入れる。

最終編集ではForced Alignment等を使って前後の「はい」を除去し、本文の最初と最後を切らない。

Episode 005で有効だった方法だが、Episode 006では制作ルールとして参照されず一度抜けた。チャットの記憶に依存せず、音声生成時に必ずこの節を参照する。

### 共通ルールとEpisode固有設定を分ける

「はい＋ロングポーズ」は共通制作ルール。一方、Episode 006の `shortstory → 1 → 2 → 3 → 4 → 5` という音声順序は006固有。共通ルールとEpisode固有設定を混ぜない。

### 最終音声タイムラインを正本にする

字幕、章タイトル、Canvas、Remotion演出の時刻をそれぞれ独立して管理しない。完成音声を組み直した後に一度だけ最終タイムラインを作り、すべての映像要素をそこから派生させる。旧動画の絶対時刻をそのまま移植しない。

### 字幕の改行と句読点

Episode 006の人間レビューでは、行頭が句読点から始まる箇所と不自然な改行が見つかった。全編レンダー前の字幕確認で、`video/remotion/docs/AI通訳ラジオ_Caption-Layout-Rule_v0.1.md` の最終確認に沿って、行頭の句読点と意味の切れ目に沿った改行を点検する。

### 観察点：Opus 5.5の役割（固定ルールではない）

Episode 005〜006の試験では、Opus 5.5は単なるCanvasコード生成だけでなく、どこを動画にするか、どこは動かさないか、何を誤解させてはいけないか、Canvas / Remotion / 静止画の選択、サイズや余白、書き出し方法、変更による二次影響まで判断できた。

現時点では「映像ディレクター＋Canvas実装者」として扱うのが有力。ただし固定化しすぎず、Season 2でも再現性を見る。

## 保存と完了の境界

- 台本：`episodes/epXXX-slug/script.md`
- 制作側Knowledge Master：`episodes/epXXX-slug/research.md`
- 現在地：必要な段階で `context/CURRENT.md` を更新
- 猫の足跡：自然に現れた観察がある場合だけ `context/CAT_FOOTPRINTS.md` を更新

ドラフト、編集レビュー反映、最終確認済みを区別する。人間の最終確認前に完成扱いにしない。

コミットとプッシュは、依頼または明示的な許可がある場合だけ行う。
